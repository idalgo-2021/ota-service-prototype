# ИИ-сервис 

Вспомогательный ИИ-сервис для OTA-бэкенда (см. `backend`).

**OTA-бэкенд** — остаётся источником истины о каталоге предложений, отзывах и других данных.

Текущая функциональность ИИ-сервиса:  
1. ИИ-ассистент (текстовый) с функциями: 
    - поиска предложений объектов проживания;
    - поиска продуктов (товары, туры, экскурсии);
    - консультирования клиентов по вопросам отелей и путешествий;
    - оформления броней и заказов (только для авторизованных пользователей).
2. Подготовка саммари-сводок по отзывам клиентов.
3. Подготовка сводок об отелях для детекции разочарований клиентов (и получения рекомендаций), т. е. определения сильных расхождений данных из отзывов с описанием объектов (составленным отельерами).

## Особенности

1. **ИИ-сервис** имеет свою базу данных и не подключается напрямую в базу OTA-бэкенда (всё взаимодействие строится на использовании HTTP API обоих сервисов).

---

2. **ИИ-ассистент**

- поддерживает только текстовый режим;
- использует публичные и пользовательские инструменты OTA API (в т. ч. JWT-токены авторизованных пользователей);
- использует инструменты поиска в Интернете (ограниченно);
- не имеет доступа к административным эндпоинтам OTA API;
- для поддержки возможности переписки с ИИ-ассистентом OTA API имеет специальные эндпоинты;
- имеет существенные ограничения по тематике выполняемых запросов;
- использует набор инструкций в виде md-файлов;
- реализован на фреймворке **smolagents** (ToolCallingAgent).

    
    *Технические детали реализации ИИ-ассистента:*

    - Ассистент реализован в `src/ai_service/infrastructure/assistant.py`.
    - Правила и шаблон запроса находятся в `src/ai_service/prompts/assistant.md` и `src/ai_service/prompts/assistant_task.md`.
    - Ограничения инструментов задаются в Python-коде.

    В обычной гостевой сессии ассистенту доступны:

    | Инструмент | Назначение и ограничения |
    | --- | --- |
    | `search_destinations` | Находит направления по названию города или региона. Не предназначен для поиска отеля, адреса, номера или койки. |
    | `search_accommodation_types` | Находит тип жилья, например отель или хостел; выбранный тип передаётся в поиск жилья. |
    | `search_accommodations` | Ищет жильё в заданном направлении, с нужным типом, расстоянием от центра и, если заданы, параметрами доступности. Возвращает не более трёх вариантов. Результаты могут содержать `review_summary`, оценки и число отзывов. Саммари передаётся целиком: для этого результата не применяется символьное усечение JSON. |
    | `get_accommodation_details` | Получает актуальную карточку конкретного объекта по его внутреннему идентификатору. |
    | `check_available_rooms` | Проверяет доступные номера/койки и цены на конкретные даты для выбранного объекта. |
    | `search_products` | Ищет туры, экскурсии и другие продукты. Если задано направление, поиск ограничивается им; по умолчанию показывается не более трёх вариантов, технический максимум — шесть. |
    | `get_product_details` | Получает актуальную карточку выбранного продукта. |
    | `resolve_calendar_date` | Возвращает текущую дату в `ASSISTANT_TIMEZONE`, вычисляет дату из фразы пользователя и день недели. Используется для дат поездки и бронирования. |
    | `search_weather_forecast` | Ищет прогноз только на `weather.com`, `gismeteo.ru` и `yandex.ru/pogoda`; результаты с других доменов отбрасываются. |

- Только авторизованному пользователю доступны `prepare_booking_confirmation` и `prepare_product_order_confirmation`. Они сохраняют точные параметры предложения, но сами не создают бронь и не меняют заказ. После явного подтверждения пользователя действие выполняет приложение через OTA API. Подготовка заказа продукта ограничена двумя вызовами за один ответ ассистента.
- Ограничения: `CHAT_MAX_STEPS` (12 по умолчанию), `CHAT_MAX_HISTORY_MESSAGES` (12), сообщение пользователя — до 4 000 символов, ответ — до 12 000. Поиск жилья возвращает до трёх вариантов, продуктов — до шести; ассистент учитывает запрошенное количество в этих пределах. Код может закрепить распознанные направление и тип жилья.
- Ассистент должен отвечать на языке гостя, опираться на каталог, не выдумывать цены и доступность, не показывать внутренние ID и оформлять бронь или заказ только после подтверждения. При наличии `review_summary` он учитывает саммари целиком; отсутствие саммари не означает отсутствие отзывов.
- Настройки ассистента: `ASSISTANT_LLM_MODEL_ID`, `ASSISTANT_LLM_API_BASE`, `ASSISTANT_LLM_API_KEY`, `ASSISTANT_LLM_TEMPERATURE`, `ASSISTANT_AGENT_LOG_LEVEL`, `ASSISTANT_TIMEZONE`, `CHAT_MAX_STEPS`, `CHAT_MAX_HISTORY_MESSAGES`. Значения по умолчанию заданы в `src/ai_service/config.py`.
- Для авторизованного чата backend передаёт JWT, который ИИ-сервис использует для запросов к OTA и получения имени пользователя. Гость работает без JWT. История разделена по владельцам, а подтверждённые действия выполняет прикладной слой чата через OTA API.

--- 

3. **Подготовка саммари-сводок по отзывам клиентов**

- строится только на основании отзывов клиентов о проживании (отзывы о продуктах не обрабатываются);
- **обрабатываются только отзывы о проживании в Санкт-Петербурге в объектах ближе 0.5 км от центра города (`distance_from_center_km < 0.5`, хардкод)**;
- **для каждого объекта недвижимости обрабатывается только 50 (последних) отзывов (хардкод)**;
- обработка реализована в виде последовательного запуска двух утилит вручную — утилиты импорта отзывов из OTA и утилиты саммаризации (отправляющей батчи отзывов для анализа в LLM);
- для импорта отзывов в OTA-сервисе утилита импорта использует специальный сервисный эндпоинт, а также выделенную сервисную роль и секрет в заголовке (пользователям эндпоинт недоступен);
- после получения результатов от LLM саммари сохраняется в ИИ-сервисе для последующей передачи в OTA (для этого ИИ-сервис имеет специальный эндпоинт API);
- настройки для LLM находятся в специальных md-файлах;
- после необходимых стадий тестирования процесс легко встроить в пайплайн и запускать как регламентный процесс (в данный момент до этого далеко).


    *Технические детали подготовки саммари-сводок:*

    - Код реализован в `src/ai_service/application/reviews.py`.
    - Правила и шаблон запроса находятся в `src/ai_service/prompts/review_summary.md` и `src/ai_service/prompts/review_summary_task.md`.
    - Ограничения инструментов задаются в Python-коде.

    - Код импортёра выбирает объекты Санкт-Петербурга с `distance_from_center_km < 0.5` и запрашивает до 50 последних опубликованных отзывов (`created_at DESC`) каждого. Отзывы о продуктах не загружаются. Выбранные ID сохраняются в `review_samples`.

    - Для каждого объекта LLM получает один батч. В запрос входят `positive_review`, `negative_review`, `overall_rating`, `cleanliness_rating`, `staff_rating`, `comfort_rating`, `location_rating`, `sleep_rating`, `bathroom_rating`, `wifi_rating`, `trip_purpose`, `party_type`, `accommodation_type` и `nights`. Дата создания используется только для выбора; `updated_at`, ID и автор не передаются. Саммари пересчитывается при изменении отзывов или версии промпта; повторный запуск с теми же данными не вызывает LLM. При превышении контекста старые отзывы исключаются целиком. Ошибки повторяются при следующем запуске.

    - Саммаризация использует настройки `REVIEW_SUMMARY_LLM_MODEL_ID`, `REVIEW_SUMMARY_LLM_API_BASE`, `REVIEW_SUMMARY_LLM_API_KEY` и `REVIEW_SUMMARY_LLM_TEMPERATURE`, задаваемые в секретах. 

        Запуск импорта: 
        - `make worker-import-once` (из папки `ai-service`) или `make -C ai-service worker-import-once`

        Запуск саммаризации: 
        - `make worker-summarize-once` (из папки `ai-service`) или `make -C ai-service worker-summarize-once`



4. **Подготовка сравнительных сводок для детекции разочарований клиентов**

- строится только для активных объектов проживания, у которых есть закреплённый отельер и заполнено саммари;
- обработка реализована в виде последовательного запуска двух утилит вручную — утилиты импорта данных об объектах (саммари отзывов, агрегированные оценки, описание и теги) из OTA и утилиты детектирования разочарований (отправляющей снапшот объекта и программную оценку рейтингов на анализ в LLM);
- настройки для LLM находятся в специальных md-файлах;
- для импорта данных об объектах для детекции в OTA-сервисе утилита импорта использует специальный сервисный эндпоинт, а также выделенную сервисную роль и секрет в заголовке (пользователям эндпоинт недоступен);
- после получения результатов от LLM результаты детекции сохраняются в ИИ-сервисе для последующей передачи в OTA (для этого ИИ-сервис имеет специальный эндпоинт API);
- LLM определяет смысловые расхождения и формирует рекомендации, а сервис рассчитывает итоговый статус проблемы и уровень критичности (`severity`) для последующего информирования отельера через OTA;
- после необходимых стадий тестирования процесс легко встроить в пайплайн и запускать как регламентный процесс (в данный момент до этого далеко).


    *Технические детали подготовки сравнительных сводок для детекции разочарований клиентов:*

    - Код реализован в `src/ai_service/application/disappointment_detection.py`.
    - Правила и шаблон запроса находятся в `src/ai_service/prompts/disappointment_detector.md` и `src/ai_service/prompts/disappointment_detector_task.md`.
    - Ограничения инструментов задаются в Python-коде.

    Детектор использует те же настройки из секретов `REVIEW_SUMMARY_LLM_MODEL_ID`, `REVIEW_SUMMARY_LLM_API_BASE`, `REVIEW_SUMMARY_LLM_API_KEY`, `REVIEW_SUMMARY_LLM_TEMPERATURE`, что и саммаризатор. 
    Порог рекомендации и пороги негативного сигнала настраиваются через `DISAPPOINTMENT_RECOMMENDATION_OVERALL_RATING`, `DISAPPOINTMENT_MIN_RATING_COUNT`, `DISAPPOINTMENT_LOW_OVERALL_RATING`, `DISAPPOINTMENT_CRITICAL_OVERALL_RATING`, `DISAPPOINTMENT_LOW_DIMENSION_RATING` и `DISAPPOINTMENT_DIMENSION_GAP`. 
    Инструкции модели находятся в `src/ai_service/prompts/disappointment_detector.md`.

    Модель возвращает признак смыслового расхождения `semantic_discrepancy`, текстовые доказательства (`evidence`) и списки рекомендаций по сервису, описанию и тегам. Итоговый статус (`status: issue / no_issue`) и уровень серьёзности (`severity`) рассчитываются кодом сервиса на основе смыслового анализа и программной оценки рейтингов (`rating_assessment`). Синхронизацию уведомлений отельерам выполняет уже OTA-бэкенд отдельной регламентной задачей.


    Запуск импорта: 
    - `make worker-disappointment-import-once` (из папки `ai-service`) или `make -C ai-service worker-disappointment-import-once`


    Запуск детекции: 
    - `make worker-disappointment-detect-once` (из папки `ai-service`) или `make -C ai-service worker-disappointment-detect-once`


## Архитектура сервиса

- База данных — PostgreSQL
- Основной язык сервиса — Python 3.12+
- HTTP API — FastAPI
- Агентский фреймворк — smolagents (от Hugging Face)

Код разделён на слои:

- `domain` — модели предметной области и интерфейсы зависимостей;
- `application` — сценарии чата, обработки отзывов и детектирования расхождений;
- `infrastructure` — интеграция с OTA API, LLM и PostgreSQL;
- `presentation` — HTTP API на FastAPI.



## HTTP API

- `GET /health` — проверка доступности процесса.
- `GET /ready` — проверка готовности и подключения к базе данных.
- `POST /api/v1/chat` — запрос к текстовому ассистенту. Требует заголовок `X-Internal-API-Key`. Для авторизованного пользователя дополнительно передаются парные заголовки `X-Assistant-User-ID` и `Authorization: Bearer <token>`. Тело запроса: `{"message": "...", "session_id": null}`. В ответе возвращаются `session_id`, текст ответа (`message`), рекомендации (`recommendations`), быстрые ответы (`quick_replies`) и статусы броней/заказов.
- `GET /internal/v1/review-summaries?limit=100&offset=0` — страница готовых сводок для OTA. Запрос требует заголовок `X-Internal-API-Key`.
- `GET /internal/v1/review-summaries/{entity_type}/{entity_id}` — получить сохранённую сводку. `entity_type` принимает `listing` или `product`. Запрос требует заголовок `X-Internal-API-Key` со значением `AI_INTERNAL_API_KEY`.
- `GET /internal/v1/disappointment-analyses?limit=100&offset=0` — постранично получить актуальные результаты детектора для импорта в OTA. Запрос требует `X-Internal-API-Key`.
- `GET /internal/v1/disappointment-analyses/{listing_id}` — получить актуальный результат по UUID объекта с тем же внутренним ключом. Если анализ отсутствует или его отпечаток не совпадает с текущими данными объекта, возвращается `404`.

Документация API:
- Swagger UI: http://localhost:8090/docs
- ReDoc: http://localhost:8090/redoc
- OpenAPI JSON: http://localhost:8090/openapi.json


## Настройка и локальный запуск

Нужны Python 3.12+, доступ к PostgreSQL и OTA API. Все команды выполняются из каталога `ai-service`:

```bash
make setup
```

Команда создаёт `.venv`, устанавливает зависимости и при необходимости копирует `.env.example` в `.env`. Заполните `.env`: параметры подключения к БД, учётные данные OTA-робота `ai_robot`, `AI_INTERNAL_API_KEY` (согласованный с OTA-бэкендом) и ключ модели LLM.

### Вариант 1. Локальная разработка (API в Python, БД в Docker):

```bash
make db-up     # запустить только базу данных PostgreSQL (порт 55432)
make migrate   # применить миграции
make run       # запустить API локально с hot-reload (Ctrl+C для остановки)
make down      # остановить базу данных и освободить ресурсы
```

### Вариант 2. Запуск целиком в Docker (БД и API):

```bash
make build     # собрать Docker-образ ИИ-сервиса
make up        # запустить базу данных и API в контейнерах
make logs      # смотреть логи контейнеров
make down      # остановить все контейнеры сервиса
```

API будет доступен на `http://localhost:8090`.

### Фоновые задачи воркера (`src/ai_service/worker.py`)

Воркер обслуживает два независимых регламентных пайплайна:

```bash
# ----------------------------------------------------------------------
# 1. Пайплайн отзывов (объекты СПб ближе 0.5 км от центра)
# ----------------------------------------------------------------------

# Полный цикл по отзывам: скачивание до 50 отзывов на каждый объект и сразу генерация саммари через LLM
make worker-once

# Либо те же два этапа по отдельности:
# Этап 1. Скачивает из OTA до 50 последних отзывов на каждый объект и сохраняет в локальную БД
make worker-import-once

# Этап 2. Отправляет батчи отзывов в LLM, формирует краткие саммари и кэширует их по хэшу данных/промпта
make worker-summarize-once


# ----------------------------------------------------------------------
# 2. Пайплайн детекции разочарований отелей
# (требует наличия отельера и уже готового саммари отзывов)
# ----------------------------------------------------------------------

# Этап 1. Импортирует из OTA свежий снапшот объекта: описание, теги, оценки и готовое саммари
make worker-disappointment-import-once

# Этап 2. Рассчитывает числовые просадки, передаёт снапшот в LLM для выявления смысловых
# противоречий и формирует рекомендации для отельера
make worker-disappointment-detect-once
```
